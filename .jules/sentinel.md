## 2024-05-24 - [Path Traversal in FAISS Deserialization]
**Vulnerability:** A path traversal vulnerability existed in `modules/validation.py` where a user-controlled `store_path` could be arbitrary directories. `FAISS.load_local` with `allow_dangerous_deserialization=True` would then load files from these arbitrary locations, resulting in a potential RCE risk.
**Learning:** Functions doing dangerous deserializations (like `pickle` in Python, heavily used by AI tools) must only ever operate on strictly validated paths that guarantee no user input can influence the location.
**Prevention:** Always validate user-provided paths with `os.path.commonpath([abs_vector_dir, abs_store]) == abs_vector_dir` before passing it to any IO functions, especially deserializations.

## 2024-05-25 - [Path Traversal in Flashcard Generation / FAISS Cache]
**Vulnerability:** A critical path traversal vulnerability existed in `modules/rag_pipeline.py`. The `get_cached_faiss_store` and `retrieve_context` functions took `store_path` arguments which were user-controlled (e.g. from `/api/flashcards/generate` which took `vector_store_path` directly). These were passed to `FAISS.load_local` with `allow_dangerous_deserialization=True`, allowing arbitrary file reading/deserialization.
**Learning:** Even if some validation exists in `modules/validation.py` (`safe_retrieve_context`), direct calls to vulnerable functions (like via `/api/flashcards/generate` -> `create_flashcards_from_store` -> `retrieve_context` -> `get_cached_faiss_store`) bypass that validation. Validation must happen as close to the dangerous sink as possible.
**Prevention:** Always add path traversal validation (`os.path.commonpath`) directly inside the function performing dangerous deserialization or file I/O, rather than relying on callers to sanitize paths beforehand.
